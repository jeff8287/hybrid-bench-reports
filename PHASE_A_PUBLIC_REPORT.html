하이브리드 CPU 에서 pandas 빠르게 돌리기

Intel Lunar Lake (P+E 하이브리드 CPU) 에서 32 종의 pandas 데이터 처리 작업을 측정 → 어떻게 코어를 나눠 써야 가장 빠른지 자동 추천하는 모델을 만들었습니다.

핵심 결론 한 줄

8 종 → 32 종 측정으로 확장한 결과, 자동 코어 분배 모델의 정확도가 43% → 81% 로 향상됐습니다.

1. 무엇을 한 건가요?

배경: 하이브리드 CPU 가 뭔지

요즘 Intel CPU 는 두 종류 코어가 섞여 있습니다.

  • P-core (Performance 코어): 빠르고 전력 많이 씀. 복잡한 계산에 좋음.
  • E-core (Efficient 코어): 느리지만 전력 적게 씀. 가벼운 작업에 좋음.

Lunar Lake CPU 는 4 P + 4 E = 8 코어 구성입니다.

문제: 데이터 처리 작업을 8 코어에 어떻게 나눠야 할까?

pandas (Python 의 데이터 분석 라이브러리) 작업을 8 코어에서 병렬 처리할 때:

  • P-core 만 쓰면? 일부 작업은 빠르지만 절반의 CPU 가 놀음
  • E-core 만 쓰면? 모든 코어 사용하지만 P 의 속도 못 살림
  • 50:50 으로 데이터 나누면? E 가 늦게 끝나면서 P 가 기다림
  • 그럼 얼마나 P 에 더 많이 분배해야 최적일까?

우리의 시도

  1. 32 종 pandas 작업 측정 (filter, sort, merge, group by, ...)
  2. 각 작업이 1 P-core vs 1 E-core 에서 얼마나 빠른지 비교 → "PE 비율"
  3. 다양한 (P 개수, E 개수) 조합 에서 시간 측정 → 곡선 모양 추출
  4. 작업들을 유사한 그룹 (cluster) 으로 묶음 → 그룹 별 모델 학습
  5. 모르는 작업이 들어오면 어느 그룹인지 추측 → 그룹 모델로 코어 분배 추천

3. 발견한 4 가지 작업 유형

작업의 코어 확장 곡선 (1 코어 → 8 코어 사용 시 얼마나 빨라지는가) 을 분석하니 4 그룹으로 자연 분리됐습니다.

유형 1: "정상적인 작업들" (Linear) — 23 종

대부분의 작업이 여기 속함. filter, column_arith (사칙연산), groupby (집계), dt_year (날짜 추출), 문자열 검색 등.

  • 1 코어 → 8 코어 = 5-6 배 빨라짐 (이론 최대 8 배)
  • 모든 8 코어 사용 이 최적
  • P:E 비율은 거의 1:1 ~ 1.5:1

유형 2: "해시 테이블이 무거운 작업들" (Hash/IO mixed) — 6 종

merge (테이블 결합), large groupby (200K 그룹 이상).

  • 1 → 8 코어 = 2-3 배만 빨라짐
  • 해시 테이블이 CPU 캐시보다 커서 메모리 접근이 병목
  • P-core 가 약간 더 유리 (PE 비율 1.5:1)

유형 3: "정렬 작업들" (Sort) — 2 종

sort_descending, multi_column sort.

  • 1 → 8 코어 = 5-6 배 빨라짐 (의외로 잘 분할됨)
  • 그러나 마지막에 결과를 다시 정렬해야 함 → 그 시간이 큰 부분

유형 4: "독특한 외톨이들" (Outliers) — 2 종

groupby_agg_int_key: 200K 개 그룹으로 묶기. 다중 코어가 오히려 느림 (캐시 충돌)

read_parquet_full: 파일 읽기. 디스크 I/O 가 병목 → 코어 늘려도 안 빨라짐

4. 주요 시각 자료

4.1 작업별 PE 비율 분포

각 작업이 P-core 대비 E-core 에서 얼마나 느린지 (1.0 = 같음, 2.0 = E 가 2 배 느림).

다중 모드 분포: 0.9 부근 (P/E 차이 미미) 과 1.5 부근 (P 가 50% 빠름) 의 봉우리. groupby_agg_int_key 만 1.9 (P 가 거의 2 배 빠름).

4.2 코어 확장 곡선 (cluster 별)

각 유형의 코어 확장 패턴.

유형 1 (linear): 이론값 (대각선) 에 가까움. 유형 4 (outliers): 그래프 위로 안 올라감.

4.3 P/E 분배 최적값 (작업별)

각 작업의 가장 빠른 코어 조합 (P 개수, E 개수).

대부분 P4E4 (모든 8 코어) 가 최적. 일부 P4E3 (E 1 개 휴식) 또는 P1E0 (단일 P-core, 캐시 충돌 작업).

4.4 모델 일반화 성능

제외된 작업의 시간을 다른 작업들로부터 추측 (LOOCV) 했을 때 평균 오차 (낮을수록 좋음).

  • 빨간 점선: 15% 기준 (이 아래면 성공)
  • 파란색: cluster 모델로 예측한 작업들 → 23/27 = 85% 성공
  • 빨간색: 별도 처리 outlier → 모델 형식 자체 부적합

Total 26/32 = 81% 통과.

8. 자주 묻는 질문 (FAQ)

Q: 왜 P-core 가 E-core 보다 항상 빠르지 않나요?

A: 단일 코어 비교 시 P 가 빠르지만, 메모리 대역폭 (BW) 이 병목인 작업은 P/E 차이 미미. 또한 E-cluster L2 캐시가 4MB 라 small workload 에선 충분.

Q: groupby_agg_int_key 가 왜 1 코어가 가장 빠른가요?

A: 그룹 200K 개의 해시 테이블 ~ 32MB. CPU LLC (Last Level Cache) 가 12MB 라 메모리 접근 폭증. 코어 추가 시 같은 캐시 라인 경쟁 → 더 느려짐 (anti-scaling).

Q: read_parquet_full 이 코어 늘려도 안 빨라지는 이유?

A: 디스크 → 메모리 데이터 이동이 병목. CPU 가 idle 상태로 IO 기다림. 디스크 throughput 한계.

Q: 32 종 다음은 얼마나 확장할 수 있나요?

A: 측정 시간이 작업당 ~1.5h (24 cells × 13 reps × 2 SFs). 100 종 = ~150 시간 = 일주일 측정. 현실적 한계.
