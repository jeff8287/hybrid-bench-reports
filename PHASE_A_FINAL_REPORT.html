bpd Phase A — Hybrid CPU PE Ratio 예측 모델

작성일: 2026-05-15 Project: bpd (Balanced Pandas) on Intel Lunar Lake Phase: A (final, comprehensive narrative) 저자: 이경태

본 보고서는 시도한 실험 순서대로 기술하지 않습니다. 최종 결과에 도달한 논리적 스토리 로 재구성했습니다. 측정/분석/시행착오의 시계열적 기록은 각 stage 의 개별 report 참조.

🎯 한 줄 요약

Intel Lunar Lake (4P+4E) 하이브리드 CPU 에서, sample DataFrame 만으로 pandas API 의 최적 P:E 분배 비율을 자동 추천하는 모델을 만들었다. 32 APIs × 3 SFs (1, 2, 5) 측정, LOOCV 81%, SF-aware cluster model + 2 per-API outliers + 2-cell light-calibration protocol 로 unseen API 도 처리.

0. 풀려는 문제

0.1 하드웨어 사실

항목 값
CPU Intel Core Ultra 7 256V (Lunar Lake)
P-cluster 4× Lion Cove @ ~5.0 GHz
E-cluster 4× Skymont @ ~3.7 GHz (Low Power Island)
L3 cache P-cluster only: 12 MB (E는 미공유)
DRAM 16 GB LPDDR5x-8533, on-package, 단일 컨트롤러 P/E 공유

핵심: P와 E는 서로 다른 클러스터지만 같은 DRAM 컨트롤러를 공유한다. 이게 cross-cluster contention 의 근원.

0.2 풀고 싶은 질문

df = pd.read_parquet("lineitem.parquet")  # 어떤 크기든

result = df.filter(...)  # 어떤 pandas API든

→ 이걸 P-cluster 와 E-cluster 에 어떻게 데이터를 나눠 분배해야 가장 빠른가? - 균등 분배 (각 코어에 1/8): P 가 idle 또는 E 가 bottleneck - P 쪽에 더 많이 (PE ratio > 1): 워크로드/데이터 크기에 따라 다름

자동화 가능한가?

1. 핵심 가설과 검증 전략

가설 H1 — Behavioral clustering

"200+ pandas API 가 비슷한 scaling 행동 을 보이는 작은 수의 cluster 로 묶인다. cluster 별 단일 모델로 새 API 도 예측 가능."

가설 H2 — Offline + sample-online inference

"Cluster 분류는 offline 측정으로, 데이터-스케일 영향은 sample_df 기반 online 추론."

가설 H3 — DRAM bandwidth-bound contention

"P/E cross-cluster slowdown 은 LLC가 아닌 DRAM bandwidth 공유에서 발생 (P/E L3 미공유 사실). 단일 scalar γ 로 모델링 가능."

검증 전략

  • TPC-H 32 APIs 측정 (cluster 학습)
  • 3 scale factors (SF=1/2/5 = 6M/12M/30M lineitem rows)
  • 24-cell contention grid ((n_p, n_e) ∈ {0..4}² \ {(0,0)})
  • 13 reps/cell (3 warmup + 10 measured)
  • In-distribution LOOCV + Out-of-distribution unseen API test

2. 실험 인프라

가장 중요한 첫 의사결정. 측정값이 신뢰할 수 없으면 모든 결론이 무의미.

2.1 4-layer CPU Affinity Lockdown

1. 환경변수: POLARS_MAX_THREADS=1, OMP_NUM_THREADS=1, MKL_NUM_THREADS=1
2. pyarrow.set_cpu_count(1) at worker entry
3. Windows SetProcessAffinityMask() via ctypes
4. OS thread affinity (메인 스레드)

→ 워커 subprocess 가 지정 코어 밖으로 migrate 불가능. PMU 측정 보장.

2.2 bpd.recycle — Process-state drift 방지

관찰 (260403_rowwise_read_io/06-vtune-profiling): 같은 워크로드를 한 process 에서 15 trials 연속 실행 → wall time +39% drift (heap fragmentation + buffer cache 누적).

해결: 매 trial 마다 fresh Python interpreter subprocess. - pandas/pyarrow import 부터 새로 - inter_trial_sleep = 2.0s (DRAM cooldown) - 13 reps = 3 warmup + 10 measured

3. 32 APIs — TPC-H workload 선정

3.1 선정 기준

  • TPC-H Q1-Q22 에서 등장하는 pandas operations
  • 4가지 dtype family 커버: int64, decimal128, date32, varchar
  • 데이터 크기 3단계: SF=1 (6M rows), SF=2 (12M), SF=5 (30M)
  • 외부 lookup: orders, customer, partsupp (TPC-H 표준)

3.3 왜 dtype variant 를 포함했나

같은 algorithmic structure 라도 dtype 에 따라 cost 가 다름: - filter (int64 비교) ≠ filter_decimal (decimal128 비교, ~3x 비싼 compare) - filter_string_eq (varchar ==) 도 다른 cluster 가능성

→ Cluster boundary 가 dtype 에 robust 한지 측정으로 검증.

4. Discovery 1 — Curve-shape Features

문제: 어떤 입력으로 cluster 를 정의할 것인가?

4.1 Attempt 1 (실패): Point feature

초기 시도 (8 APIs, K=3): - raw_pe_ratio (P/E single-core 속도비) + alpha_P + merge_share - K-means K=3, silhouette 0.47 - LOOCV: 3/7 = 43% PASS ❌

실패 원인: - C0 cluster 에 merge_inner_multikey (α=0.43, sub-linear) + dt_year (α=0.89, near-linear) 같이 들어감 - 둘 다 raw_pe_ratio ≈ 1.5 라서 같은 cluster — 하지만 scaling 행동은 정반대 - 외부 review (Codex): "Point feature 부족, 곡선 모양 필요"

4.2 Attempt 2 (성공): Curve-shape feature

핵심 통찰: PE ratio 결정에 정말 중요한 정보는 "P 가 몇 배 빠른가" 가 아니라 "코어 수 늘릴 때 어떻게 scaling 하는가".

예시 — 두 워크로드의 P-cluster scaling:

        P1    P2    P3    P4         Pattern
ws_A:  100   53    38    28          ideal linear (~4x speedup at P4)
ws_B:  100   85    80    75          saturated (~1.3x speedup at P4)

둘 다 raw_pe_ratio 같아도 PE 분배 결과는 완전히 다름.

4.3 5 Curve-shape Features

Feature 정의 무엇을 capture
α (alpha_P_scaling) log(t_P1 / t_P4) / log(4) P-cluster intra-scaling exponent. 1.0=ideal, 0.0=no scaling, 음수=anti-scaling
β (beta_E_scaling) log(t_E1 / t_E4) / log(4) E-cluster intra-scaling. P와 동일 형식
γ (gamma_proxy) 1 − (1/t_P4E4) / (1/t_P4 + 1/t_E4) cross-cluster interference. 0=independent, 1=완전 충돌
log1p(merge_share) log1p(t_merge / t_max at P4E4) parent merge cost 비중. sort 류는 크다
log1p(anti_score) log1p(t_P4E4 / t_best) P4E4 가 best 가 아닌 정도 (≥1 if P4E4 not best)

4.4 결과 (32 APIs, 5 features, K-means K=4)

  • Silhouette 0.535
  • LOOCV: 26/32 = 81% PASS, mean MAPE 11.4%
  • 2x improvement vs point feature

→ H1 (behavioral clustering) 검증: scaling exponent 가 곧 cluster identity.

4.5 Static features 는 왜 cluster input 에서 제외했나

dev/260507_api_pe_model/02-feature-extraction/_features.py 가 추출하는 29 개 static feature (nrows, dtypes, cardinality, OI 등) 가 있지만, clustering input 으로는 단 하나만 사용 (io_strategy, IO outlier 검출용). 나머지는 informational only. 각 feature 의 제외 이유:

Feature 후보였던 이유 제외 이유
input_dtype_ratio_* (5 bins: numeric/decimal/datetime/string/other) dtype 이 비용 좌우 Categorical bin → OOD void: 사용자가 새 dtype (e.g., pd.Float32, pd.Int8, pd.CategoricalDtype) 으로 호출 시 어느 bin 에도 안 떨어짐. 대체로 continuous input_avg_bytes_per_element + binary input_has_decimal 채택
OI / oi_estimate (Operational Intensity) Roofline model 표준 metric pandas 에서 무용: pandas operator 는 거의 memcpy + comparison (FLOPs ≈ 0) → OI 모든 API 에서 ≈ 0 → cluster 분리력 0
vtune_memory_bound_pct, vtune_dram_bw_avg_gbs (VTune Top-down) OI 보다 더 적합한 cause 신호 8 APIs only 측정, 32 APIs 확장 미완. correlation analysis 미수행 → 추가 후보 features 로 검토 (Phase B)
selectivity_estimate filter 류 비용 좌우 Workload-specific: filter / str_endswith 에만 존재. 모든 cluster 에 invariant 한 feature 아님 → category-conditional 한 feature 는 K-means input 부적합
nrows, input_nbytes 데이터 크기 (cost 의 핵심 driver) Absolute scale → predict-time online inference 로 분리: 측정값은 데이터 크기에 dependent 하지만, sample_df 의 len() 으로 SF 추론 후 SF-specific raw_pe_ratio 적용. cluster 분류는 SF-invariant 한 모양 으로.
raw_pe_ratio (Stage 03 calibration) P/E single-core 속도비 α, β 와 redundant: α 는 t_P1/t_P4, β 는 t_E1/t_E4 — 동일 측정값에서 raw_pe_ratio (= t_E1/t_P1) derivable. K-means 의 euclidean distance 가 같은 정보를 두 번 받아 weight 왜곡. K=3 silhouette: 7-feature (full) 0.22 → 4-feature (subset) 0.25 → 3-feature (core) 0.47 — feature 줄일수록 silhouette 향상 (실험 §5.2.3 cluster_features.csv 참조)
nbytes, avg_row_bytes, output_rows_estimate, output_n_cols 데이터/결과 크기 모두 absolute scale, point measurement. scaling regime 의 모양 정보 없음
merge_strategy, splittable, arity, is_inplace, lookup_table Workload metadata (categorical) 분류 자체에 categorical bin 문제. 또한 cluster identity 가 algorithmic taxonomy 와 다르다는 것이 §5.3 의 발견 — merge_anti 가 C_linear, sort_values_multikey_mixed 가 C0_hash 같은 패턴. 즉 metadata 로 cluster 못 정함
ops_per_row_estimate (VTune-calibrated) 명령어 수 (compute 지표) 측정은 했지만 Python+pandas+pyarrow wrapper overhead (~4000-5000 inst/row) 가 모든 워크로드 floor → operator 간 차이 약함. cluster 분리력 제한적

핵심 원칙 5가지 (static feature engineering 교훈)

  1. Curve-shape > point measurement: cluster identity 는 "P 가 몇 배 빠른가" (1 차원) 가 아니라 "코어 추가 시 어떻게 scaling 하는가" (다차원 곡선 모양). α, β, γ 가 이 모양을 capture.
  2. OI 는 pandas 에서 무용: FLOPs ≈ 0. Roofline-style compute-intensity metric 은 numerical kernels 용. pandas 는 메모리-바운드라 "memory_bound %" 가 필요하지만 VTune 32 APIs 측정 미완.
  3. Categorical bins 는 위험: OOD void (unseen dtype/strategy) 생성 → continuous feature (avg_bytes_per_element) 대체.
  4. Skewed feature 는 log1p 필수: K-means euclidean distance 가 outlier (sort 류의 merge_share, anti-scaling 의 anti_score) 에 끌려가지 않도록.
  5. Absolute scale 은 online inference 로: sample_df 가 매번 다른 크기로 호출되므로, cluster 분류는 SF-invariant 한 정보로, 데이터 크기 효과는 predict-time _infer_sf() 로 분리.

결론

  • Cluster input 5 features (모두 측정 derived, scaling-shape) + Outlier 검출 1 static bit (io_strategy) = 모델의 진짜 입력
  • 나머지 29 static features 는 informational only (Stage 02 features.csv 에 저장되어 분석/디버깅용으로 보존)
  • Phase B 후보: VTune memory_bound_pct / dram_bw 32 APIs 확장 + correlation gate (|r| ≥ 0.6) 통과 시 6번째 clustering feature 로 승격

5.2 각 cluster 의 의미

C_linear (25 APIs, 78%) — Compute-bound

  • Working set ≪ L3 (12 MB)
  • 코어 수에 거의 비례한 speedup
  • P4E4 가 항상 best cell, ~5-6x speedup vs P1
  • Representative scenario: 단순 row-wise transform (filter, arithmetic, datetime extraction)

C0_hash (5 APIs, 16%) — Memory-bound

  • Hash table / sort buffer 가 L3 초과
  • Sub-linear scaling (~3x speedup max)
  • DRAM bandwidth bottleneck
  • γ=0.49 (high cross-cluster contention)

C2_anti — Anti-scaling (singleton)

  • groupby_agg_int_key: l_partkey 200K groups × hash entry → ~16 MB hash table
  • L3 = 12 MB → hash table 이 LLC 초과
  • 다중 코어가 같은 hash bucket update → cache line ping-ponging
  • 단일 P-core 가 가장 빠름 (P1E0 권장)
  • α=-0.34 → power-law cluster model 자체 부적합 → per-API fallback

IO Outlier

  • read_parquet_full: disk → page cache → decompress → pandas
  • Hash 와 같은 curve shape 같지만 physics 가 다름
  • Per-API fallback (P0E4 권장: E-cluster 가 IO 병렬화에 충분)

5.3 Behavioral vs Algorithmic Classification

놀라운 발견: 사람의 직관 (algorithmic taxonomy) 과 measured behavior 가 다른 경우 존재.

  • sort_values_multikey_mixed 가 C0 hash-bound 에 분류: sort 인데도 hash join 과 비슷한 contention. 이유: multi-key sort 의 partition+concat+resort 비용 패턴이 hash build+probe 와 유사
  • merge_anti 가 C_linear 에 분류: anti-join 의 dominant cost 가 filter (linear), not hash join

→ Empirical clustering 의 진짜 가치: 사람 직관이 놓치는 행동적 유사성 발견.

6. Discovery 3 — Cluster Identity Depends on Data Scale (가장 중요)

이게 Phase A 의 decisive finding.

6.1 Setup

  • SF=1 → 6M rows lineitem (~0.5 GB), L3 fit possible for small workloads
  • SF=2 → 12M rows (~1 GB)
  • SF=5 → 30M rows (~2.5 GB), 확실히 LLC overflow

6.2 Observation — Cluster Drift

21 fully-measured workloads at SF=5 (read_parquet_full, merge_inner_multikey partial; groupby_agg_int_key outlier excluded):

Workload α_SF1 α_SF2 α_SF5 Drift
filter 0.901 0.869 0.272 linear → linear → hash
groupby_agg 0.887 0.813 0.665 linear → linear → hash
groupby_min_max 0.949 0.777 0.654 linear → hash → hash
isin_filter 0.952 0.818 0.770 linear → linear → hash
merge_anti 0.937 0.864 0.697 linear → linear → hash
multi_column_sort_pure 0.884 0.862 0.690 linear → linear → hash
str_endswith 1.025 0.922 0.714 linear → linear → hash

14 workloads stable, 7 workloads drift → 67% SF-stability.

6.3 가장 충격적 사례: filter SF=1→SF=5

SF=1 filter:  α=0.901, near-linear, P4E4 best, 6x speedup
SF=5 filter:  α=0.272, near-saturation, P4E4 best but only ~2x speedup

같은 algorithm, 같은 dtype, 다른 데이터 크기 — 완전히 다른 regime.

원인: 30M rows × 16 cols boolean mask + indexing = ~2.5 GB working set, L3 12 MB 의 ~200x. Cache thrash.

6.4 Best Cell Shift in Hash Family

Workload best @ SF=1 best @ SF=5
merge_inner_singlekey P4E4 P3E1 (fewer cores!)
merge_left_outer P4E3 P1E3 (E-cluster favored)
merge_chain_3tables P4E1 P1E3
merge_anti P4E3 P2E4

→ Hash join 류는 SF=5 에서 E-cluster (separate L3) 가 상대적으로 유리. P-cluster 의 L2 cache thrashing 이 더 심하기 때문.

6.5 함의

Phase A 초기 (SF=1+SF=2 만) 의 잘못된 결론: "32/32 cluster SF-stable". 사실은 SF=1↔SF=2 에서만 그렇고, SF=5 까지 확장하면 7/21 (33%) drift.

→ Cluster identity 는 working set size 에 의존. 단일 cluster assignment 모델 부적합.

8. Discovery 5 — Light-Calibration Protocol for New APIs

문제: Production 환경에서 unknown pandas API 호출 시 어떻게 cluster 분류?

8.1 후보 protocol 들

Protocol Cells 측정 Features 비용 정확도
Static-only 0 nrows, dtype 등 정적 정보 0 미검증
2-cell (P1, P4) 2 α only ~5-10 min 검증함
4-cell 4 α, β, raw_pe ~10-20 min redundant
5-cell (full) 5 α, β, γ_partial, merge_share ~15-30 min overkill

8.2 Tier 1 검증: α-only 가 충분한가?

기존 32 training APIs 에 대해 α-only 분류 시뮬레이션:

Step 1 (static, free): io_strategy == 'read' → OUTLIER_IO
Step 2 (P1, P4 측정): α = log(t_P1 / t_P4) / log(4)
Step 3 (분류):
    α < 0       → C2_anti       (single core best)
    α < 0.80    → C0_hash       (sub-linear regime)
    α >= 0.80   → C_linear      (near-linear)

결과 (training data): - α threshold sweep 0.79 ~ 0.84: 31/32 = 97% match (read_parquet_full 만 fail, IO 정적 검출로 cover) - 결합 protocol: 32/32 = 100%

8.3 Feature Separability 분석

Feature C0_hash max C_linear min Gap 평가
α 0.785 0.843 0.058 ✅ Cleanest separator
β 0.743 0.761 0.019 ✅ Tiny gap
γ 0.590 0.106 -0.484 ❌ Overlap (linear의 일부도 high γ)

→ α 가 가장 강한 cluster separator. β, γ 추가 도움 적음.

8.4 Tier 2 검증: 5 진짜 unseen APIs

TPC-H에 없는 5 pandas operators 측정:

API LC α (10 reps) FG α (24 cells) LC cluster FG cluster Match?
cumsum -0.252 ✗ noise +0.820 C2_anti C_linear ❌
pivot_table +0.888 +0.817 C_linear C_linear ✅
rank_dense +1.043 +1.030 C_linear C_linear ✅
rolling_mean +0.227 -0.048 C0_hash C2_anti ❌
shift +1.006 +0.752 C_linear C0_hash ❌

2/5 match (40%) — boundary fragility 노출.

8.5 진단

원인: short workload (< 100ms) 의 10-rep 측정 noise. cumsum 의 LC α=-0.25 는 outlier 1개 (111.7ms) 가 median 을 왜곡한 결과.

Sanity check (cumsum, 50 reps): - t_P1 = 28.1ms (CV 5.3%) - t_P4 = 9.8ms (CV 21.1% — short workload variance) - α = +0.758 → C0_hash (FG +0.82 와 ±0.06 일치) - Anti-scaling 가설 폐기

8.6 진짜 finding: rolling_mean genuine anti-scaling

LC: α=+0.23 (sub-linear), FG: α=-0.05 (anti-scaling)

  • best cell = P1E4 (NOT P4E4)
  • γ=0.55 (high contention), anti_score=1.78
  • Window function 의 cross-row memory access pattern → 다중 코어가 같은 cache lines 경쟁

→ 모델의 진짜 generalization 능력 증명 — TPC-H 에 없던 anti-scaling 패턴 자동 식별.

8.7 Production Protocol 권고

def classify_new_workload(workload_fn, sample_df):
    # Step 1 (static, 0 trials)
    if workload_fn.io_strategy in {'read_parquet', 'read_csv'}:
        return 'OUTLIER_IO'  # → recommend P0E4

    # Step 2 (measure 2 cells: P1, P4)
    # CRITICAL: if t_P1 < 100ms, escalate to 25+ reps for noise tolerance
    t_P1 = measure_median(workload_fn, sample_df, n_p=1, n_e=0, min_reps=25 if quick else 10)
    t_P4 = measure_median(workload_fn, sample_df, n_p=4, n_e=0, min_reps=25 if quick else 10)
    alpha = math.log(t_P1 / t_P4) / math.log(4)

    # Step 3 (classify)
    if alpha < 0:        return 'C2_anti'    # P1E0
    elif alpha < 0.80:   return 'C0_hash'    # cluster (α=0.55, β=0.65, γ=0.49)
    else:                return 'C_linear'   # cluster (α=0.99, β=0.92, γ=0.25)

비용: ~5-10 min/API (short workloads 는 25+ reps 권장).

10. Discovery 7 — Honest Limitations

10.1 LOOCV 는 in-distribution generalization 만 측정

LOOCV: 32 TPC-H APIs → 1 hold out → refit on 31 → predict 1
       → 26/32 = 81% pass

BUT: 32 APIs 모두 TPC-H family. 진짜 unseen pandas operators (df.pivot,
     df.rolling, df.cumsum, df.melt, df.rank) 일반화는 별도 검증 필요.

→ 본 보고서의 81% 는 "TPC-H 유사 APIs 내부에서 generalize" claim 만 정당화.

10.2 Unseen API 테스트 (5 workloads) 의 한계

  • 5 APIs 는 통계적으로 작은 sample
  • 측정 protocol (boundary error 허용) 이 production-correct 비용 미반영 가능성:
  • rolling_mean: partition boundary 에서 window 잘림 (correctness 무시, timing OK)
  • pivot_table: partial pivot per partition (real production 은 outer concat 필요)
  • rank_dense: per-partition local rank (global rank 비용 미측정)

10.3 Co-run interference 미측정

현재 γ: - single workload 의 P/E 동시 실행 contention 만 capture - 실제 inter-op parallelization: op A (P-cluster) + op B (E-cluster) 동시 → cross-op interference - PCCS (MICRO'21) 의 cross-cluster external-demand combiner 미반영

→ Phase B 작업: 4 cluster representative × 4 placement × 4 cluster representative = 64-cell co-run grid (~6h).

10.4 End-to-end TPC-H query 검증 부재

  • Per-operator 측정만 완료
  • TPC-H Q1-Q22 실행 시 multi-op pipeline 에서 모델 추천이 실제 작동하는지 미확인
  • 가장 중요한 future work

10.5 단일 하드웨어

  • Lunar Lake (Core Ultra 7 256V) only
  • Arrow Lake (L3 P/E 공유) → cluster model 다를 가능성
  • Raptor Lake / Sapphire Rapids / AMD Bergamo 미검증

14. 결론

14.1 무엇을 증명했나

  1. H1 검증: Pandas API 들은 작은 수의 behavioral cluster 로 묶인다 (K=4 hybrid, 32/32 covered).
  2. H2 검증: Cluster 분류 = offline, 데이터 스케일 = online inference (sample_df.shape[0] → SF → cluster).
  3. H3 검증: P/E cross-cluster contention 은 단일 scalar γ 로 capture (R²_test 0.94-0.95 for C_linear/C0_hash).
  4. Curve-shape feature 우월성: Point feature (43% LOOCV) → curve-shape (81% LOOCV), 2x improvement.
  5. SF-aware cluster drift: 데이터 크기 가 cluster identity 결정. 7/21 workloads at SF=5 drift to hash regime.
  6. Light-calibration protocol: 2 cells + 1 static bit → 100% cluster classification on training data, 40% on unseen (boundary fragility documented).
  7. Boundary robustness: Cluster misclassification 시에도 MAPE 9-13% (cluster coefficient 가 boundary 에서 smooth).

14.2 무엇을 못 증명했나

  1. Truly unseen pandas API 일반화 — 5 APIs 만 테스트 (df.pivot, rolling, cumsum, rank, shift). Cluster classification 40% match.
  2. Co-run interference — single-workload contention 만 측정. Op-pair interference 미측정.
  3. End-to-end TPC-H query — per-operator 만. Q1-Q22 multi-op pipeline 효과 미검증.
  4. 다른 하드웨어 일반화 — Lunar Lake LPI 만. Arrow Lake / Sapphire Rapids / AMD Bergamo 미측정.
  5. Production pandas workload — TPC-H 합성 데이터만. 실제 사용자 코드 (Kaggle notebooks 등) 미검증.

14.3 핵심 contribution (paper-ready)

  1. Lunar Lake LPI 의 첫 systematic characterization — 32 pandas APIs × 3 SFs × 24 cells = 9,216 measurement points
  2. Behavioral vs algorithmic clustering 의 실증적 비교 — sort_values_multikey_mixed 의 hash-bound 분류, merge_anti 의 linear 분류 같은 reviewer-friendly findings
  3. SF-aware cluster drift 발견 — cache pressure regime 의 정량적 demonstration
