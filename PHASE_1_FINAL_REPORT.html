Phase 1 종료: 하이브리드 CPU 의 pandas 자동 튜닝 라이브러리

Intel Lunar Lake (P+E 하이브리드 CPU) 에서 pandas 작업을 가장 빠르게 돌리는 P:E 코어 분배 비율을 자동 추천하는 라이브러리를 만들었습니다.

한 줄 결론

32 종 pandas 작업을 측정 → cluster 모델로 P:E 비율 자동 추천 → 81% 정확도로 일반화. bpd.auto_ratio.predict_ratio() API 출시.

1. 문제

하이브리드 CPU 란?

Intel Lunar Lake 같은 최신 CPU 는 두 종류 코어가 섞여 있습니다.

  • P-core (Performance 코어) 4 개: 빠르지만 전력 많이 씀
  • E-core (Efficient 코어) 4 개: 느리지만 전력 적게 씀

총 8 코어를 어떻게 활용할까가 문제입니다.

데이터 처리 시 딜레마

pandas 작업 (예: filter, sort, merge) 을 8 코어에 병렬 분배할 때:

  • 50:50 균등 분할 → E 가 늦게 끝나면서 P 가 idle (낭비)
  • P 에 100% 몰빵 → 4 P-core 만 사용, 절반의 CPU 노는 셈
  • 올바른 비율 (예: 1.5:1) → 모든 코어가 동시에 끝남 (최적)

작업마다 최적 비율이 다른데, 사용자가 매번 어떻게 알지?

2. 우리의 해법

자동 추천 API

from bpd.auto_ratio import predict_ratio
import pandas as pd

df = pd.read_parquet("lineitem.parquet")
rec = predict_ratio("filter", df)

print(rec.pe_ratio)        # 0.985  ← 추천 P:E 비율
print(rec.cluster_label)   # "linear-scalable"
print(rec.outlier)         # False

8 종 → 32 종 작업 측정 후 cluster 모델 학습 → 모르는 작업도 어떤 그룹인지 추측해서 비율 추천.

외톨이 작업 처리

일부 작업은 cluster 모델이 부적합 → 별도 처리:

rec = predict_ratio("groupby_agg_int_key", df)
print(rec.outlier)           # True
print(rec.recommendation)    # {'best_cell': 'P1E0', 'best_n_p': 1, 'best_n_e': 0}
print(rec.warnings)          # ['Anti-scaling: 다중 코어가 오히려 느림']

→ "이 작업은 단일 P-core 만 쓰라" 명확하게 알려줌.

4. 발견한 4 가지 작업 유형

작업의 코어 확장 곡선 (1 코어 → 8 코어 사용 시 얼마나 빨라지는가) 으로 자연 분리.

C0: "해시/IO 혼합" (5 종)

merge_inner_singlekey/multikey, merge_left_outer, merge_chain_3tables, sort_values_multikey_mixed. - 1 → 8 코어 = 2-3 배 빨라짐 - 해시 테이블 캐시 압박 + IO 일부 영향

C1: "정상적인 작업들" — Linear scalable (23 종)

filter family, column_arith, dt_year/month/day, groupby_, str_, case_when_, isin_filter, merge_anti 등. - 1 → 8 코어 = 5-6 배 빨라짐 - 모든 8 코어 사용 (P4E4) 이 최적 - 대부분의 일반 작업이 여기 속함*

C2: "이상한 작업" — Anti-scaling (1 종)

groupby_agg_int_key (groupby(l_partkey).agg(...)). - 코어 늘릴수록 오히려 느려짐! - 200K 그룹 해시 테이블 = 32MB > CPU 캐시 → 캐시 충돌 - single P-core 가 가장 빠름

C3: "정렬 작업" — Sort with merge (2 종)

sort_descending, multi_column_sort_pure. - 1 → 8 코어 = 5-6 배 빨라짐 - 단, 마지막에 결과를 다시 정렬해야 해서 그 시간이 큰 비중

5. 정확도 검증 (LOOCV)

Leave-One-Out Cross-Validation: "이 작업을 처음 보는 척" 하고 다른 작업들로부터 예측 가능성 검증.

Approach Pass count Mean MAPE
원본 8 APIs (K=3) 3/7 = 43% 28%
Phase A 32 APIs (K=4 hybrid) 26/32 = 81% 11.4%

→ 1.9 배 통과율 향상.

잔여 fails (6 종)

근본적 한계 (2 종, 별도 처리됨): - groupby_agg_int_key (anti-scaling): per-API lookup - read_parquet_full (IO-bound): per-API lookup

Borderline cluster fails (4 종): - merge_chain_3tables 17%, merge_inner_multikey 21%, sort_values 19%, sort_descending 18% - 추가 작업 측정으로 개선 가능 (Phase 2 future work)

@dataclass(frozen=True)
class PERatioRecommendation:
    pe_ratio: float              # 0.5 - 4.0 추천 비율
    cluster_id: int              # 0-3 (-1: unknown)
    cluster_label: str           # "linear-scalable" 등

11. FAQ

Q: 32 종 측정에 49 시간이 너무 길지 않나요?

A: 한 번만 측정하면 됨 (offline). 사용자는 predict_ratio() 호출 비용만 부담 (~수 ms).

Q: 다른 하드웨어에서도 작동하나요?

A: Lunar Lake (4P+4E) 측정값만 들어있어 다른 CPU 에서는 작동 안 함. 다른 하드웨어 → 같은 방법으로 재측정 필요 (자동화 가능).

Q: 32 종 외 새 API 는 어떻게 처리되나요?

A: 안전한 default (pe_ratio=1.0) 반환 + warning. 정확도 보장 안 됨. Phase 2 에서 self-calibration 자동화 검토.

Q: 측정 시간 절감 방법 있나요?

A: Phase 2 에서 self-calibration (작업당 ~30 초 mini-measurement) 으로 첫 호출 시 자동 calibrate + cache 검토 중.

Q: 라이브러리 라이선스는?

A: 본 연구는 academic context (서울대학교 KT-NIA 협력 과제). 코드 공개 검토 중.
