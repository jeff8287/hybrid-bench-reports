Phase 3 Report — API expansion (8 → 17 APIs), BW-aware Latency Prediction

Date: 2026-05-24 Branch: master Predecessor: Phase 2 Report (8 APIs, pccs_k2 best 12.26% MAPE) Sweep duration: 18h 17m (SF=1 full + SF=2 quick, PID 5872)

TL;DR

  1. Phase 3 best MAPE: 6.06% (pccs_k3 with self_BW, 17 APIs SF=1) — Phase 2 best 12.26% 의 절반.
  2. PCCS formula 회복: Phase 2 의 16.98% (실패) → Phase 3 의 11.02%. Phase 3 의 wider self_BW range (0.34-20.46 GB/s vs Phase 2 의 5-17) 가 PCCS knee-shift mechanism 을 비로소 작동시킴.
  3. self_BW 의 가치 입증: BW-only pooled_pw 7.13% → self_BW-aware pccs_k3 6.06% (1pp 개선). Phase 2 에서는 좁은 range 때문에 self_BW 가 무의미했음.
  4. 측정 안정성도 한 몫: 같은 8 APIs 의 Phase 2 → Phase 3 = 12.84% → 7.69% (warm JIT, thermal stable). pure model engineering 으로는 ~1-2pp.
  5. SF=2 (larger data) 는 여전히 어려움: 14% 근처. Cross-SF generalization 별도 필요.

추가된 9 API 효과: - groupby_agg_int_key: self_BW 0.34 GB/s (compute-bound 확정, hash 가 cache 안에서 돌고 DRAM access 거의 없음) - read_parquet_full/col: self_BW 4-7 GB/s (parquet decompress 가 dominant — 예상 IO heavy 보다 훨씬 낮음) - 이 둘이 self_BW lower bound 를 dramatically 확장.

핵심 비교

  1. 같은 8 API, 측정 reproduction: Phase 2 → Phase 3 → MAPE 12.84% → 7.69% (Δ−5pp). measurement noise 가 model engineering 보다 큰 영향.

  2. 8 → 17 APIs: 7.69% → 7.13% (Δ−0.6pp). 변형 추가의 marginal value.

  3. SF=1 vs SF=2: 7.13% (SF=1, 17 APIs) → 14.62% (SF=2, 16 APIs). SF=2 가 2배 어려움. - SF=2 quick 모드 데이터 적음 (4 K × 4 reps vs 10 K × 10 reps) - 큰 데이터 = 더 복잡한 cache pattern = 더 nonlinear slowdown - read_parquet_full SF=2 P1: idle 13s → K0 71s (slowdown 5.4x, SF=1 의 1.98x 보다 훨씬 큼)

5. Discussion

Q1: 9 새 API 가 PCCS knee-shift 모델 살릴까?

Phase 2 결론: PCCS 4-param formula 가 좁은 self_BW range (5-17 GB/s) 에서 17% MAPE — too rigid. Phase 3 (BW-only) 에선 pooled_pw 가 7.13% — PCCS formula 자체가 필요 없을 가능성 시사.

하지만 emon self_BW 측정 후에 다시 검증해야 함: - 17 APIs 의 self_BW range 가 Phase 2 의 5-17 GB/s 보다 정말 넓어졌는지 - 그러면 PCCS formula 가 회복되는지

(이 검증은 Phase 3.5 — admin shell 생기면 실행)

Q2: SF=2 가 왜 더 어려운가?

가능한 이유: - Cache eviction: SF=2 lineitem ~14 GB > L2/L3 (Lunar Lake L3 = 12 MB) — 모든 데이터가 DRAM 에서 stream - Bandit interference shape 바뀜: 더 큰 working set 이 더 많은 cache eviction → Bandit 의 cache footprint 가 victim 의 cache 에 영향 (PCCS 의 "source-obliviousness" 가정 깨질 가능성) - Quick mode 데이터 부족: 4 K levels 만으로 knee 찾기 어려움

중요 implication: scheduling 모델이 SF (working set size) 에 dependent.

Q3: Linear vs piecewise — 차이 크지 않음

Phase 3 SF=1 17 APIs: linear 10.70% / pooled_pw 7.13% → 3.6pp 차이. Phase 2 (8 APIs): 15.67% / 12.84% → 2.8pp 차이.

→ piecewise 가 좋긴 하지만 dramatic 차이 아님. linear fit (단 2-parameter) 도 ~10% MAPE 가능 — scheduler integration 시 충분히 가벼움.

7. Limitations

  1. emon self_BW 미측정: 새 9 APIs 의 self_BW 가 정말로 Phase 2 의 5-17 GB/s range 를 확장하는지 미검증 (admin 필요)
  2. SF=2 데이터 부족: quick mode (4 K × 4 reps) 가 model fitting 에 부족. SF=2 full 모드 필요 시 약 4h.
  3. Phase 2 측정 noise 의 근본 원인 미정: thermal/JIT/state 중 어느 게 dominant 인지 모름
  4. K_LEVELS_FULL 의 K=K0 이 SF=2 에서는 BW 더 높음 (62 GB/s vs 55 GB/s SF=1) — Bandit pressure 가 victim 영향에 따라 달라짐
  5. Bandit 자체의 cache footprint: 200 MB array × 7 threads = 1.4 GB > L3 — pure-BW 가정 깨질 수 있음

Range expansion: Phase 2 [5.4, 17.6] → Phase 3 [0.34, 20.46] (50x wider on low end).

groupby_agg_int_key 0.34 GB/s 가 핵심 발견 — 200K hash bucket 이 L2 (4MB shared) 에 들어가 DRAM access 거의 없음. 일반적 "groupby = memory-bound" 직관 깨짐.

SF=1 vs SF=2 self_BW (PCCS source-obliviousness 가정 검증): - column_arith P1: 20.46 (SF=1) → ~similar (SF=2, larger but BW saturates) - groupby_agg_int_key P1: 0.34 → 0.60 (SF=2) — 데이터 커지며 일부 hash bucket 이 L2 evict → DRAM access 증가 - read_parquet_*: SF=1 ≈ SF=2 (rate 동일)

→ 대체로 rate invariant, 단 cache-bound API 는 working set 영향 받음.
