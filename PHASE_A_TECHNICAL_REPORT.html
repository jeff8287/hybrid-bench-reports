Phase A — 예측 모델 / Contention / Feature Engineering 종합 기술 리포트

작성일: 2026-05-13 대상: bpd (Balanced Pandas) Phase A 전체 (Stage 00 ~ 08) 프로젝트: Intel Lunar Lake hybrid CPU 환경에서 pandas API 별 P/E ratio 자동 추천 모델 총 측정 데이터: 49h wall, 22,464 trials (warmup 포함), 32 workloads × 24 cells × {SF=1, 2, 5 부분}

0. Executive Summary

0.1 무엇을 만들었나

  • 공개 API: bpd.auto_ratio.predict_ratio(workload, sample_df) — pandas operator 이름과 데이터 샘플을 입력 받아 추천 P/E 코어 비율 + cluster label + outlier 플래그를 반환
  • 모델 구조: K=4 K-means cluster + 2 per-API outlier (hybrid)
  • 정확도: LOOCV 81% (26/32 통과 ≤ 15% MAPE), mean MAPE 11.4%
  • 실현 speedup: 32 APIs 평균 4.79x (P1 baseline 대비, model 추천 cell 적용 시)

0.2 핵심 발견

  1. Curve-shape feature (스칼라 PE ratio가 아닌 scaling exponent α, β, γ)이 point feature보다 cluster 분리축으로 결정적으로 우월. 동일 클러스터링 알고리즘으로 LOOCV 43% → 81% 향상.
  2. 데이터 부족(8 APIs)이 일반화 실패의 근본 원인. 32 APIs 확장 후 cluster boundary 명확. 측정 데이터가 부족하면 어떤 알고리즘으로도 일반화 불가능.
  3. Lunar Lake P/E의 cross-cluster contention은 LLC가 아닌 DRAM bandwidth에서 발생 (P-cluster ↔ E-cluster L3 미공유). γ는 이 단일 scalar interference를 capture.
  4. Anti-scaling outlier 존재 (groupby_agg_int_key, α=-0.34): single core에서 가장 빠름. 모든 power-law cluster model로 fit 불가능 → per-API fallback 필수.
  5. IO-bound outlier 존재 (read_parquet_full, α=0.23): hash-bound cluster와 같은 곡선 모양이지만 다른 physics → per-API fallback.

0.3 한계 (정직한 보고) — 반드시 §7.2 와 함께 읽을 것

  • ⚠️ LOOCV 는 in-distribution generalization 만 검증: 32 APIs 모두 TPC-H family. 한 개 빼서 나머지 31 개로 예측 → "쉬운 거에서 몇 개 안 보이게 한 것". 진정한 unseen API (df.pivot, df.rolling, df.cumsum 등) 일반화는 미검증. 자세한 분석은 §7.2.2 ~ §7.3.
  • Co-run interference 미측정: 현재 γ는 single workload의 P/E 동시 실행 시 contention만 capture. operator A와 B를 동시에 실행 시 cross-op interference는 별도 grid 측정 필요 → Phase B.
  • VTune memory features 미통합: FW-6b에서 8 APIs DRAM BW/memory-bound %는 측정했으나 clustering input 아님 (informational only). 32 APIs 확장 + correlation check 후 통합 결정 필요.
  • End-to-end TPC-H query 검증 부재: per-operator 측정만 완료. TPC-H Q1-Q22 end-to-end 실행 시 모델 추천이 작동하는지 미확인.
  • 단일 하드웨어: Lunar Lake (Core Ultra 7 256V) 만. Arrow Lake / Raptor Lake / Sapphire Rapids 미검증.

1. 연구 목표와 가설

1.1 풀려는 문제

  • Intel hybrid CPU (P-core + E-core)에서 pandas API를 병렬화할 때, P와 E에 얼마나 다르게 데이터를 분배해야 최적인가?
  • 단순 균등 분배 (PE ratio = 1.0) 는 P-core가 늘 idle 또는 E-core가 늘 bottleneck — 비효율.
  • 이상적인 PE ratio는 워크로드, dtype, 데이터 크기에 따라 다름 — 어떻게 자동으로 결정할 수 있나?

1.2 가설

  • H1 (intra-op clustering): pandas operator는 P/E scaling 거동에 따라 작은 수의 cluster로 자연 분리되며, cluster별 단일 (α, β, γ) coefficient로 새 API를 일반화 가능하다.
  • H2 (offline + sample-online): cluster 결정은 offline 측정으로, 데이터-스케일은 sample_df에서 online 추론 가능하다.
  • H3 (Lunar Lake LPI contention model): P/E cross-cluster contention은 DRAM bandwidth 공유에서 옴 (L3 미공유). 따라서 single scalar γ로 capture 가능하다.

1.3 Goal vs Non-goal

Goal (Phase A): - 32 pandas APIs (TPC-H + 보조)에 대해 per-API PE ratio 추천 모델 구축 - Cluster-based 일반화 (LOOCV) - bpd 라이브러리 공개 API

Non-goal (Phase A): - Inter-op parallelization (독립적 op들의 코어 할당) — Phase B - Co-run interference (op A와 op B 동시 실행 시 slowdown) — Phase B - TPC-H end-to-end query 실행 검증 — Tier 4 - pandas 외 backend (polars/modin) — out of scope

2.3 측정 인프라

2.3.1 4-layer CPU Affinity Lockdown

각 워커 subprocess는 다음 순서로 affinity 적용:

  1. 환경변수 (subprocess spawn 전): POLARS_MAX_THREADS=1, OMP_NUM_THREADS=1, MKL_NUM_THREADS=1, OPENBLAS_NUM_THREADS=1
  2. pyarrow runtime: pyarrow.set_cpu_count(1) (워커 entry point 시작)
  3. Windows process affinity: SetProcessAffinityMask() ctypes → 지정 코어만 사용
  4. OS thread affinity: 메인 thread를 affinity mask로 묶음

→ 단일 core에서 한 subprocess 가 다른 core로 migrate 되지 않음. PMU 측정 보장.

2.3.2 bpd.recycle — Process-State Drift 방지

dev/260403_rowwise_read_io/06-vtune-profiling/ 에서 관찰된 현상: - 동일 워크로드 (pandas read_csv 10GB)를 한 process 에서 15 trials 연속 실행 → wall time +39% 누적 inflation - 매 trial을 fresh subprocess 로 실행 시 → drift ~0% - 원인: pandas/numpy heap fragmentation + buffer cache 누적

bpd.recycle.run_trials() 의 핵심: - 매 trial 마다 새 Python interpreter subprocess 생성 - subprocess 내부에서 pandas import 부터 새로 (warm cache 의도적 회피) - inter_trial_sleep = 2.0s (DRAM cooldown) - 13 reps = 3 warmup + 10 measured

2.3.3 CPU Affinity 검증

매 trial 종료 시: - psutil.cpu_percent(percpu=True) 0.1초 간격 샘플링 - 각 core 의 avg/max 계산 - target core avg > 50% AND non-target core avg < 10% → PASS - FAIL 시 해당 trial 폐기 + 재측정

2.3.4 결과 안정성 (AC-04 verdict)

Stage 4 전체: - 19,968 measured trials - 7,635 unique PIDs (subprocess recycling 정상) - 0 affinity match fails - 0 duckdb violations (no duckdb leaked into measurement) - 0 cell hash disagreements - 0 error trials (timeout 600s 적용 후)

3. 워크로드 설계: 32 APIs

3.1 선정 기준

  • TPC-H 쿼리에서 등장하는 pandas API 만 + dtype variant 포함
  • dtype: int64, decimal128, date32, varchar (TPC-H 4 dtype family 모두 커버)
  • 데이터 크기: SF=1 (~6M rows lineitem), SF=2 (~12M), SF=5 (~30M) — cache pressure 단계
  • 외부 lookup: orders.parquet, customer.parquet, partsupp.parquet (TPC-H 표준)

3.2 32 APIs 전체 명세

소스: bpd/ops/tpch_ops.py. 모든 워크로드는 TPC-H lineitem 테이블의 partition 을 입력으로 받음 (단, IO 워크로드는 파일 경로 받음).

3.2.1 Filter family (6) — 행 선택 (row selection)

# API 하는 일 dtype 특성 TPC-H
1 filter df[df['l_shipdate'] <= '1998-09-02'] — 단일 date 컬럼 비교 date32[day] q1
2 between_filter 3-AND: date BETWEEN + decimal BETWEEN + numeric < date + decimal + int q6
3 isin_filter df[df['l_shipmode'].isin(['AIR','REG AIR','SHIP','TRUCK'])] — 4-value membership varchar q12
4 multi_cond_filter 3-AND on 3 different columns (date + decimal + int) mixed q6
5 filter_decimal df[df['l_quantity'] > 25] — 단일 decimal128 비교 decimal128 q6 부분
6 filter_string_eq df[df['l_shipmode'] == 'AIR'] — 단일 varchar equality varchar q19/q12 부분

왜 6개?: 같은 "filter" semantic 이라도 dtype 따라 비교 비용이 매우 다름 (int < date < decimal < varchar). cluster boundary 가 dtype 에 의존하는지 검증.

3.2.2 Groupby family (6) — 키별 집계

# API 하는 일 그룹 cardinality TPC-H
7 groupby_single_key_string groupby('l_returnflag').agg(sum, mean, max) ~3 그룹 q5 form
8 groupby_count groupby('l_shipmode').size() ~7 그룹 q4 form
9 groupby_nunique groupby(['l_returnflag','l_linestatus']).l_orderkey.nunique() ~4 그룹 × distinct 카운트 q16 form
10 groupby_min_max groupby('l_returnflag').agg(min='l_discount', max='l_discount') ~3 그룹 q15 form
11 groupby_agg groupby(['l_returnflag','l_linestatus']).agg(sum_qty, sum_price, count, max) — q1 표준 ~4 그룹 q1
12 groupby_agg_int_key ⚠️ groupby('l_partkey').agg(...) — 200,000 그룹 (= L3 초과) ~200K 그룹 q11/q15 form

왜 6개?: 그룹 cardinality 가 hash table 크기를 결정. low cardinality (3-7 그룹) 은 L1 fit, high cardinality (200K 그룹) 은 L3 초과 → 다른 contention regime. groupby_agg_int_key 는 anti-scaling outlier 의 발견 케이스.

3.2.3 Merge family (5) — 두 테이블 join

# API 하는 일 hash table 크기 TPC-H
13 merge_inner_singlekey df.merge(orders, on='l_orderkey', how='inner') orders 0.18 GB q3/q4
14 merge_inner_multikey df.merge(partsupp, on=['l_partkey','l_suppkey'], how='inner') partsupp 0.03 GB q5 form
15 merge_left_outer df.merge(orders, on='l_orderkey', how='left') 같음 + NULL 처리 q13 form
16 merge_anti df where l_orderkey NOT IN orders (indicator merge + filter) 같음 q22 form
17 merge_chain_3tables df ⋈ orders ⋈ orders (3-table chain) 누적 큼 q3/q5 form

왜 5개?: hash table 크기 + key complexity (single int vs composite) + join semantic (inner / left / anti / chain) 각자 다른 contention 패턴.

3.2.4 Sort family (3) — 정렬

# API 하는 일 sort 비용
18 sort_values_multikey_mixed 3개 컬럼 sort, mixed asc/desc, 다른 dtype (decimal/decimal/int) 가장 비싼

3.3 핵심 설계 결정

3.3.1 dtype variant 포함

이유: 같은 algorithmic structure 라도 dtype에 따라 cost가 다름. - filter_decimal: decimal128 비교 (vs filter: int64) — VECTOR_CMP_EQ 비용 ~3x - filter_string_eq: varchar == (vs filter: int64) — column-level string compare - case_when_int_input vs case_when: input dtype 차이 - case_when_string_output: result dtype 차이 (output materialization 비용)

→ 6 filter variants → cluster내 dtype-induced variation 검증

3.3.2 cardinality variant 포함

  • groupby_agg: l_orderkey (~1.5M groups, low cardinality per group)
  • groupby_agg_int_key: l_partkey (~200K groups, mid cardinality)
  • groupby_count / groupby_nunique / groupby_min_max: 다른 aggregation operator

→ cardinality 차이가 cluster boundary 흔드는지 검증 (결과: groupby_agg_int_key가 outlier 됨, 그 외는 모두 C1 linear)

3.3.3 join 복잡도 variant

  • merge_inner_singlekey: l_orderkey (lineitem ⋈ orders)
  • merge_inner_multikey: (l_partkey, l_suppkey) ⋈ partsupp (composite key)
  • merge_left_outer: NULL-handling overhead
  • merge_anti: filter via anti-join
  • merge_chain_3tables: 2-stage join (lineitem ⋈ orders ⋈ customer)

→ hash table 크기, key compare cost, multi-stage pipeline 효과 cover

4.3 Stage 02 — Static Feature Extraction

dev/260507_api_pe_model/02-feature-extraction/_features.py

4.3.1 추출 features (29 per workload)

4.6 Stage 05 — Categorization (Clustering)

4.6.1 무엇을 하려는 건가 (intuition 먼저)

문제: 32 APIs 각각에 대해 따로 PE ratio 모델을 만들면 — 미래에 새 API (예: df.pivot_table) 가 추가됐을 때 대응 불가. 일반화 (generalization) 가 필요.

아이디어: pandas operator 들을 비슷한 행동을 보이는 그룹 으로 묶고, 그룹별로 하나의 모델 을 만들자. 새 API 가 들어오면 어느 그룹에 속하는지 판정 후 그 그룹 모델로 예측.

문제: 어떤 기준으로 "비슷"한지 정의해야 함. 4가지 후보: 1. Algorithmic taxonomy (사람이 분류): "filter 류", "groupby 류" — 인간 직관 기반 2. Cylon 5-pattern: embarrassingly parallel, globally reduce, shuffle-compute, ... — 학계 표준 분류 3. Point feature 클러스터링: P/E 단일 속도비 (raw_pe_ratio) 같은 스칼라 1개로 K-means 4. Curve-shape feature 클러스터링: scaling curve 의 모양 (α, β, γ 등 여러 값) 으로 K-means

Phase A 는 (4) 채택. 이유는 §5.1, §5.2 의 시행착오 기록 참조.

4.6.2 K-means 가 하는 일 (쉽게)

각 API 를 다차원 공간의 점 (point) 로 봄. 좌표는 그 API 의 feature 값들: - API filter → (α=0.91, β=0.88, γ=0.20, merge_share=0.04, anti_score=1.0) - API merge_inner_singlekey → (α=0.69, β=0.72, γ=0.55, merge_share=0.18, anti_score=1.1)

K-means 알고리즘: 1. K 개의 중심점 (centroid) 을 임의로 잡음 2. 각 API 점을 가장 가까운 중심점에 할당 3. 같은 중심점에 할당된 점들의 평균 위치로 중심점 이동 4. 더 이상 변하지 않을 때까지 2-3 반복

결과: 32 APIs 가 K 개 cluster 로 분리. 각 cluster 내 점들은 서로 가깝고, 다른 cluster 점들과는 멀다.

4.6.3 K 를 몇으로 정할 것인가 — Silhouette score

Silhouette score 는 cluster 분리 품질을 0 ~ 1 로 표현하는 지표: - 각 점에 대해: (다른 cluster 까지 평균 거리 - 같은 cluster 내 평균 거리) / max(둘) - 모든 점의 평균 = silhouette score - 1.0 에 가까우면 매우 명확하게 분리, 0.0 이면 cluster 구분 없음, 음수면 잘못 분류

rule of thumb: silhouette ≥ 0.5 는 "강한 cluster 구조", 0.25 ~ 0.5 는 "합리적", < 0.25 는 "분리 약함".

4.6.4 K 선택 — K=2 부터 K=7 까지 sweep

5 features (α, β, γ, log1p(merge_share), log1p(anti_score)) 을 z-score normalize 후 K-means 실행:

K Silhouette Inertia SF=1↔SF=2 stability 해석
2 0.666 80.6 — "linear vs problematic" 이분. 너무 거칠음.
3 0.633 51.4 —
4 0.535 25.5 32/32 (100%) 선택. silhouette 합리적 + SF 안정.
5 0.426 15.3 26/32 (81%) silhouette 가장 낮음. over-segmentation.
6 0.489 9.6 —

그런데 왜 K=2 (silhouette 0.666) 가 가장 좋은 게 아닌가? silhouette 만 보면 K=2 가 최고. 하지만 K=2 는 단순히 "linear-scalable vs 나머지" 로 분리하므로 너무 거침 — anti-scaling, hash-bound, sort 등 다른 contention 패턴 을 한 묶음에 넣어 cluster 별 PE ratio 예측이 불가능. K=4 가 silhouette × 실용성 의 최적.

SF stability 의 중요성: SF=1 데이터로 분류한 cluster 가 SF=2 에서도 같이 유지되는지. K=4 에서 32/32 (100%) → SF=1 측정으로 모델 만들면 SF=2 에서도 작동 가능. K=5 는 81% (6 워크로드가 SF=1↔SF=2 사이에 cluster 이동) → SF 변화에 fragile.

5.1.3 정적 feature 만으로는 부족한 이유

정적 feature 는 "이 워크로드가 어떻게 생겼는가" 만 묘사. 하지만 PE ratio 결정에는 "P 와 E 가 얼마나 다른 속도로 처리하는가" 가 필요 — 이건 측정해야 알 수 있는 동적 속성. 따라서 Gen 2 에서 calibrated feature 추가.

5.2 Gen 2 — Calibrated feature (raw_pe_ratio)

5.2.1 측정 방법 (Stage 03)

각 워크로드 × 각 SF 에 대해: - (n_p=1, n_e=0) 워커 1개 P-core 에서 측정 → t_P1_ms (median over 10 reps) - (n_p=0, n_e=1) 워커 1개 E-core 에서 측정 → t_E1_ms - raw_pe_ratio = t_E1_ms / t_P1_ms (E 가 P 대비 몇 배 느린가)

직관: raw_pe_ratio = 2.0 이면 E 가 P 의 2배 느림 → P 에 2배 데이터 줘야 균형. raw_pe_ratio = 1.0 이면 균등 분배.

5.2.2 raw_pe_ratio 분포 (32 APIs, SF=1)

  • min 0.88 (filter_string_eq) — E 가 P 보다 빠름 (예외적)
  • median 1.25 — 대부분 P 가 약간 빠름
  • max 2.05 (groupby_agg_int_key) — P 가 E 의 2x 빠름

5.2.3 Gen 2 의 K=3 clustering 시도 (8 APIs)

features: 3개 - raw_pe_ratio (point) - alpha_P_scaling (Stage 04 contention grid 에서 derived, intra-P scaling) - merge_cost_share_p4e4 (parent merge 시간 비중)

K-means K=3: silhouette 0.47

LOOCV 결과: 3/7 PASS = 43%, mean MAPE 28%

왜 실패했나? 핵심 cluster heterogeneity: - C0 cluster 에 merge_inner_multikey (α=0.43, sub-linear) 와 dt_year (α=0.89, near-linear) 가 같이 들어감 - 둘 다 raw_pe_ratio ≈ 1.5 라서 같은 cluster — 하지만 scaling 행동은 정반대 - LOOCV 시 merge_inner_multikey hold-out → C0 refit 은 dt_year 만 남음 → 새 cluster center 가 멀리 이동 → 예측 실패

교훈: point feature 하나로는 cluster 정체성을 못 잡는다. P 와 E 단일 속도비가 같아도 다중 코어로 갈 때 행동은 완전히 다를 수 있음.

이 가설을 검증하려고 Gen 3 로 진입.

5.3 Gen 3 — Curve-shape feature (32 APIs)

5.3.1 Curve-shape 이란

PE ratio 결정에 정말 중요한 정보는 "P 가 몇 배 빠른가" (단일 점) 가 아니라 "코어 수가 늘어날 때 어떻게 scaling 하는가" (곡선). 곡선 모양 자체가 contention regime 의 지문.

예시 — 두 워크로드의 P-cluster scaling:

P1: 100ms       100ms
P2: 53ms        85ms     ← 2배 빠른가? B는 안 빨라짐
P3: 38ms        80ms
P4: 28ms        75ms
   linear      saturated

둘 다 raw_pe_ratio 가 같아도 (E 측정값 동일이라 가정) scaling 곡선은 완전히 다름. A 는 linear-scalable (P 4개 다 활용 가능), B 는 hash-bound (1개 추가 효과 미미). PE 분배 시 A 는 P4E4 가 best, B 는 P1E0 가 best 일 수도 있음.

5.3.2 Curve-shape feature 5종 — 각각 무엇을 잡나

Feature 정의 무엇을 capture 직관
α (alpha_P_scaling) log(t_P1 / t_P4) / log(4) P-cluster intra scaling exponent 1.0 = ideal linear (P4 가 P1 의 1/4 시간), 0.0 = no scaling (P4=P1), 음수 = anti-scaling (P4>P1)
β (beta_E_scaling) log(t_E1 / t_E4) / log(4) E-cluster intra scaling exponent 같은 식, E-cluster
γ (gamma_proxy) 1 − observed / naive_sum at P4E4 cross-cluster interference 0 = P 와 E independent, 1 = 완전 충돌, 음수 = synergy
log1p(merge_share) log1p(t_merge / t_max) at P4E4 parent merge cost 비중 0 = parent 거의 안 함, 큰 값 = parent 가 bottleneck (sort 류)
log1p(anti_score) log1p(t_P4E4 / t_best) anti-scaling 강도 0 = P4E4 가 best, 큰 값 = best 가 적은 코어에 있음

5.3.3 왜 raw_pe_ratio 를 제외했나

수학적으로 α 와 β 와 t_P1, t_E1 이 있으면 raw_pe_ratio 는 derivable. 따로 추가하면 redundant — K-means 의 distance 가 같은 정보를 두 번 받아 weight 가 왜곡됨.

Feature subset 실험 (8 APIs, Stage 05): | subset | dim | K=3 silhouette | |---|---|---| | 7 features (모두 포함) | 7 | 0.217 (worst) | | 4 features (pe+throughput+α+merge_share) | 4 | 0.249 | | 3 features (pe+α+merge_share) | 3 | 0.473 (best) |

→ 8-sample 환경에서는 dim 줄이는 게 silhouette 결정적 영향. Gen 3 에서는 32 sample 이라 5-dim 까지 OK (silhouette 0.535).

5.3.4 Z-score normalization

K-means 는 euclidean distance 기반 → feature scale 다르면 큰 scale feature 가 distance 지배.

각 feature 를 (x - mean) / std 로 변환 → 모든 feature 가 평균 0, 분산 1 → 동등한 weight 로 cluster boundary 결정.

5.3.5 Log1p transform 이유

merge_cost_share 와 anti_score 는 skewed distribution: - 대부분 워크로드 merge_share = 0.01 ~ 0.1 (작음) - sort 류 = 1.0 ~ 10.0 (매우 큼) - 두 그룹의 distance 가 raw scale 로 ~100x → K-means 가 sort 만 분리하고 나머지는 한 cluster 로

log1p(x) = log(1 + x) 적용: - 작은 값 (0.01) → 0.01 (거의 그대로) - 큰 값 (10.0) → 2.4 - 두 그룹의 distance 가 ~100x → ~10x 로 축소

→ K-means 가 양쪽 정보를 균형 있게 사용.

5.5 Feature engineering 의 핵심 5가지 발견

  1. Point feature 는 cluster 분리 약함: 단일 cell 측정값 (raw_pe_ratio) 만으로는 scaling regime 못 구분. 곡선 모양 필요.
  2. Curve-shape feature (α, β, γ) 가 결정적: scaling exponent 가 곧 cluster identity. 같은 raw_pe_ratio 라도 α 다르면 다른 cluster.
  3. OI 는 pandas 에서 무용: FLOPs ≈ 0. 대체로 "memory-bound %" 가 필요하지만 미통합.
  4. Categorical dtype bins 위험: OOD void 생성 → continuous (avg_bytes_per_element) 대체.
  5. Skewed feature 는 log1p 필수: K-means euclidean distance 가 outlier 에 끌려가지 않도록.

6.1 Lunar Lake LPI 의 아키텍처적 사실

사실 함의

6.2 γ — Cross-Cluster Interference Proxy

6.2.1 정의

γ = 1 − (T_observed(P4E4)) / (T_naive_sum(P4E4))

where:
  T_naive_sum(P4E4) = N_rows × [w_P4 / (4·throughput_P1) + w_E4 / (4·throughput_E1)]
                    = predicted time assuming no cross-cluster interference
  T_observed(P4E4) = actual measured time at (n_p=4, n_e=4)
  • γ = 0: P와 E 가 independent 하게 실행 (no interference)
  • γ > 0: cross-cluster slowdown 존재
  • γ < 0: super-linear improvement (메모리 prefetch synergy — 드물지만 일부 워크로드에서 관찰)

6.2.2 측정값 (cluster mean)

Cluster γ 의미
C0 (hash-bound) 0.486 48.6% slowdown when P4 + E4 co-run. hash table이 DRAM BW 폭주
C1 (linear-scalable) 0.198 19.8% slowdown. compute-friendly, BW 낮음
C3 (sort-with-merge) 0.198 C1 와 비슷 — sort 자체는 compute-heavy

6.2.3 검증

Speedup model:

speedup(n_p, n_e) = [n_p^α + (1/r) · n_e^β] · (1 − γ · n_p · n_e / 16)
                                                ^^^^^^^^^^^^^^^^^^^^^^
                                                interference term
  • n_p · n_e / 16: cross-cluster 활성도 (0-1 normalized) — P4E4 일 때 1.0
  • (1 − γ · ...): 다중-cluster 활성 시 throughput de-rate

R²_test = 0.95 (C0, C1, C3 평균) → γ proxy 가 cross-cluster contention을 적절히 capture.

6.3 Anti-Scaling 발견

6.3.1 groupby_agg_int_key 의 미스터리

Stage 04 Phase A 측정 중 발견: - l_partkey (200,000 unique groups) 기준 groupby - best cell = P1E0 (single P-core). P4E4 보다 단일 P가 2x 빠름. - α = -0.34, β = -0.18 (둘 다 음수)

6.3.2 원인 분석

  • l_partkey 200K groups × hash entry (~80 bytes) = ~16 MB hash table
  • L3 = 12 MB → hash table이 LLC 초과
  • 다중 코어가 같은 hash bucket을 동시 update 시도 → cache line ping-ponging
  • 단일 코어가 hash table을 cache-resident하게 유지하는 게 더 빠름

6.3.3 모델링 한계

  • speedup(n_p, n_e) = ... · (1 − γ · ...) 형식은 항상 monotonic increasing in (n_p, n_e)
  • anti-scaling은 monotonic decreasing → 형식 자체 부적합
  • Solution: per-API fallback. predict_ratio('groupby_agg_int_key') → 항상 P1E0 lookup.

7.2 Validation — 그리고 그 한계의 정직한 분석

7.2.1 LOOCV 가 무엇인가 (그리고 무엇이 아닌가)

Leave-One-Out Cross-Validation (LOOCV): 1. 32 APIs 중 1개를 hold-out (테스트용) 2. 나머지 31 APIs 로 cluster 재fit (K-means 새로 돌림) 3. Hold-out API 가 어느 cluster 에 속하는지 판정 (가장 가까운 centroid) 4. 그 cluster 의 (α, β, γ) 로 hold-out API 의 SF=2 speedup 예측 5. 실측값과 비교 → MAPE 계산 6. 32 APIs 모두 한 번씩 hold-out 으로 만들어 반복

결과: 26/32 PASS (MAPE ≤ 15%) = 81%.

7.2.2 ⚠️ LOOCV 의 본질적 한계 — "쉬운 거에서 몇 개 안 보이게 테스트한 것"

이 critique 는 정확하다. LOOCV 는 in-distribution generalization 만 측정한다.

LOOCV 의 가정: - "Hold-out API 는 학습한 32 APIs 와 같은 분포에서 나왔다" - "Hold-out API 의 정확한 cluster 는 다른 31 APIs 가 알려준다"

이게 만족되는 이유: - 32 APIs 모두 TPC-H 쿼리에서 등장 → 같은 algorithmic family 의 다양한 variant - C1 cluster 의 23 APIs 는 모두 "row-wise simple operation" — 서로 매우 유사 - 한 개 빼도 나머지 22 개가 같은 cluster center 만들어줌 → 빠진 1 개도 그 center 근처에 있을 가능성 높음

LOOCV 가 측정하지 못하는 것 (= 진짜 unseen data 테스트): 1. 새로운 algorithmic family: pandas 200+ operator 중 TPC-H 에 안 나오는 것 — df.pivot_table, df.rolling.mean, df.expanding.sum, df.cumsum, df.melt, df.stack, df.shift, df.diff, df.rank 등. 2. 다른 backend dtype: pd.Float32, pd.Int8, pd.BooleanArray, pd.CategoricalDtype — 모두 32 APIs 에 미등장. 3. 다른 workload pattern: time-series, window function, pivoting, reshaping — Phase A 에 없음. 4. 다른 데이터 분포: TPC-H 는 균등 분포 + 합성 데이터. 실제 pandas user 의 skewed / sparse / mixed data 는 다른 contention.

7.2.3 C1 (23 APIs) 의 23/23 PASS 가 의미하는 것 — 그리고 의미하지 않는 것

의미하는 것: - C1 내부 23 APIs 가 서로 매우 유사. 한 개 빼도 다른 22 개의 cluster center 가 거의 안 움직임 → hold-out 도 그 center 에 가까움 → MAPE 작음. - "linear-scalable 워크로드들끼리는 서로 잘 예측한다" 는 약한 주장 만 가능.

의미하지 않는 것: - "새로운 linear-scalable 워크로드 (예: df.cumsum) 도 잘 예측한다" — 검증 안 됨. - "Phase A model 이 일반적인 pandas API 에 일반화된다" — 검증 안 됨.

Brutal honest 한 표현: 23/23 PASS 는 "C1 cluster 가 내부적으로 균일하다는 측정" 일 뿐, "unseen API 에 대한 generalization 증거" 는 약함. 차이를 분명히 해야 함.
